# Design

## Context

See proposal.md - Why. The requirements are in `specs/development-seed-data/spec.md`; the exact seed content is listed in the appendix below.

Relevant current state:

- `Web/Program.cs` already runs `MigrateAsync` for `CatalogDbContext` and `TripsDbContext` inside `if (app.Environment.IsDevelopment())`. The Web integration tests host the API in environment `Testing`, so nothing that runs only in Development affects them.
- `Category.Create`, `CatalogItem.Create` and `Trip.Create` always assign `Guid.CreateVersion7()`. There is no way to create a domain object with a known id.
- Category names are unique among non-removed categories and item names are unique within a category, enforced by filtered unique indexes with collation `Latin1_General_CI_AI` (archived MVP design D7).
- Catalog and Trips are separate bounded contexts (MVP design D1). Trip items are snapshots handed in by the caller (D2); `TripEndpoints.SelectCategoriesAsync` builds those snapshots from two catalog queries. Only the Web composition root sees both contexts.
- The local database lives on a persistent Docker volume and already holds test data, so seeding has to work next to existing rows.

## Goals / Non-Goals

**Goals:**

- Seed content defined once, in code, readable as the packing list it came from.
- Re-running the seed is always safe, including after the user edited seeded data.
- Seeded records are created through the domain model, so the same invariants hold as for user-created data.

**Non-Goals:**

- Importing Excel files at runtime or an import feature in the UI. The sheet is converted once, by hand, into the seed definition.
- Updating seeded records when the seed definition changes later. A changed seed name produces a new record, not an update.
- Seed data for automated tests. Tests keep creating their own data.

## Decisions

### D1: A seeder per bounded context, composed in Web

`Catalog.Infrastructure.Sql/Seeding/` gets `CatalogSeedData` (the definition) and `CatalogSeeder` (writes it through `CatalogDbContext`). `Trips.Infrastructure.Sql/Seeding/` gets `TripsSeeder`, which takes a trip definition plus `CategorySelection` snapshots and writes them through `TripsDbContext`. `Web/Seeding/DevelopmentSeeder` runs the catalog seeder first, then builds the trip selections and runs the trips seeder.

Each context stays ignorant of the other: Trips never sees catalog seed ids except as snapshot values, which is exactly how the API already feeds it (D2 of the MVP design).

*Alternatives considered:*
- Seed through the existing MediatR commands. Rejected: the commands generate their own ids, so idempotence would have to rely on name matching, which cannot tell "user renamed the seeded category" from "seed never ran".
- EF Core `HasData` in a migration. Rejected: it seeds every environment, and every later change to the list would need a new migration.

### D2: Deterministic ids from a stable key

Every seeded category and item gets a name-based UUID (version 5 style: SHA-1 over a fixed namespace GUID plus a key such as `category:Kinderen – Kleding` or `item:Kinderen – Kleding/Sokken`). The two trips use two hard-coded GUID constants in `DevelopmentSeeder`.

Ids derived from the seed names keep the definition free of 171 GUID literals, yet stay stable across runs and machines. The derivation uses the seed name, not the current database name, so a rename by the user does not change the id and the record is not re-created.

*Alternative considered:* hard-coded GUID literals for every record. Equally stable, but the definition becomes unreadable and copy-paste mistakes are hard to spot in review.

### D3: Domain factories with an explicit id

`Category.Create(Guid id, CategoryName name)`, `CatalogItem.Create(Guid id, Category category, ItemName name, Amount? amount)` and `Trip.Create(Guid id, TripName name, TripDates dates)` are added; the existing overloads delegate to them with `Guid.CreateVersion7()`. An empty GUID is rejected with an `ArgumentException`.

This keeps the seeder inside the domain rules (a category must exist and not be removed before an item can be added to it, trip items are generated by `SelectCategories`) rather than writing rows directly.

*Alternative considered:* setting the key through the EF change tracker after calling the existing factory. Rejected: it hides a domain concern inside infrastructure and breaks silently if the mapping changes.

### D4: Idempotence rules per record

Lookups ignore the soft-delete flag, so a record removed by the user still counts as existing.

- **Category**: if the id exists → leave it alone. Otherwise, if a non-removed category with the same name exists → skip the category and all its items and log a warning. Otherwise create it.
- **Item**: if the id exists → leave it alone. If its category was skipped or is removed → skip. If a non-removed item with the same name exists in that category → skip and log. Otherwise create it.
- **Trip**: if the id exists → leave the whole trip alone, including its categories and item statuses. Otherwise create it, select its categories, apply the item deletions, and save once.

The catalog is saved in a single `SaveChangesAsync`, and so is each trip, so a crash halfway never leaves a trip without its items.

### D5: Trip snapshots come from the live catalog, not from the seed definition

`DevelopmentSeeder` reads the seeded categories and items back through `ListCategoriesHandler.Query` and `ListCatalogItemsForCategoriesHandler.Query`, the same path `SelectCategoriesAsync` uses. Seeded categories that are missing or removed are left out of the selection. The mapping from DTOs to `CategorySelection` moves from `TripEndpoints` into a shared helper that the endpoint and the seeder both use.

This guarantees a trip never references a catalog item that does not exist, and the snapshot text matches what the catalog really holds.

### D6: Winter sports exclusions by source item id

The summer-only items are listed in `DevelopmentSeeder` as seed item ids. After `SelectCategories`, the seeder calls `trip.DeleteItem` for each trip item whose `SourceItemId` is in that list. Deleting through the aggregate keeps the item restorable, as the spec requires.

### D7: Startup wiring and logging

In `Program.cs`, inside the existing Development block and after both `MigrateAsync` calls, `DevelopmentSeeder.SeedAsync` runs in the same scope. It logs one information line per run with the number of inserted categories, items and trips, and one warning per skipped record that clashes with user data. Any unexpected exception stops startup, so a broken seed is noticed straight away.

## Risks / Trade-offs

- [The seed adds about 150 items and 2 trips to the existing local database next to the current test data] → Accepted. The seeded data is easy to tell apart, and it can be removed through the app like any other data, after which it stays removed (D4).
- [A later change to a seeded name creates a second record instead of renaming the first] → Accepted and documented in Non-Goals. Renaming seed entries is rare; a one-off cleanup is cheaper than an update mechanism.
- [Summer items are chosen by judgment] → The list is explicit in the appendix and lives in one place in code, so it is easy to change. Users can restore any of them on the trip.
- [Startup takes longer in Development] → One query per table plus at most one insert batch; negligible next to the container start.

## Migration Plan

No schema change and no migration. Rollback is reverting the code; seeded rows stay in the local database and can be removed through the app or by dropping the database volume.
